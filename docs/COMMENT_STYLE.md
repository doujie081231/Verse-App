# 注释规范

注释用于解释仅靠名称与控制流程难以理解的设计原因、兼容约束和接口契约。阅读顺序应是实现、必要的说明，再到设计或维护文档。

## 基本格式

- 新增的 Verse 注释使用中文；类名、API、协议和配置键保留原名。
- 行注释使用 `// 内容`，标记后留一个空格。完整解释使用完整句子，短小分组标题可不加句号。
- 公共类型、非直观接口和具有边界条件的方法使用 KDoc 或 Javadoc，首行概括职责；后续说明参数约束、返回值、异常或副作用。
- 分组标题保持简短，例如 `// 原生库搜索路径`，不使用整行等号、横线或装饰符。
- 避免重复代码含义的注释。复杂兼容逻辑说明为什么需要它、适用条件，以及删除它可能影响什么。

```kotlin
/**
 * 检查运行时目录是否具备启动所需的核心文件。
 *
 * 返回 null 表示校验通过，否则返回缺失项的说明。
 */
fun invalidReason(home: File): String?

// JNI 桥必须先完成初始化，后续窗口调用依赖它持有的类引用。
initializeNativeBridge()
```

## 说明当前行为

注释随实现一同维护。删除功能时删除失效注释；重构后更新方法名、路径、条件和初始化顺序，避免留下半句话或过时的参数说明。

将“以前怎样、后来怎么修、某次测试用了多少份日志”等开发过程留在提交记录或维护文档中。源码中保留能指导后续修改的结论，必要时链接相关问题或设计记录。

版本号和平台限制只有在决定代码分支、文件格式或协议兼容性时才写入注释。性能、兼容性与安全结论需要有实现依据或可追溯记录，避免使用“完全兼容”“一定更快”等未经验证的描述。

## 待办与停用代码

统一使用 `TODO: 具体事项` 或 `FIXME: 已知问题`，说明触发条件、影响或完成条件；已有问题编号可附在后面。不要创建没有关联问题的编号，也不要删除仍然适用的待办来掩盖未完成工作。

删除不再使用的注释代码块，由 Git 保存历史。确有必要保留的替代实现，应说明适用场景和启用条件。

## 第三方代码与兼容标识

保留版权声明、许可证正文、SPDX 标识、作者信息和明确的来源说明。清理开发笔记与重复注释不等于删除来源；不能通过改名或删除声明将第三方实现描述成独立原创。

FCL、HMCL、PojavLauncher、SDL、LWJGL 等名称可能表示真实依赖或兼容协议。涉及包名、类名、JNI 方法、布局格式与渲染器参数时保留准确名称，使用简洁说明解释当前适配关系。

上游维护的大段源码遵循原文件的注释风格。优先整理本项目增加的适配说明，避免为统一外观而制造无意义的上游差异。
